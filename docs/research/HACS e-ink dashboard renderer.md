# Render inside HA, serve TRMNL directly

The architecture to use is **a pure-Python HACS integration that draws each screen as SVG, rasterises it in-process with resvg-py, quantises it with Pillow, and serves the TRMNL firmware API (`/api/setup`, `/api/display`, `/api/log`) from Home Assistant**. It also exposes the same image as an `ImageEntity` and as a token-protected plain PNG URL for Alias, ESPHome, Kindle and BYOS clients. That is the only combination that meets every constraint at once. It installs through HACS on HA Container with no add-on and no sidecar. It adds one 1.6 MB abi3 wheel that was verified to install and run in the official 2026.11 container. It gives 0 % grey pixels on 1-bit output when anti-aliasing is switched off. A full 800×480 frame renders in about 38 ms. Browser-based approaches (Chromium, Playwright, the official TRMNL add-on, every BYOS server except one) fail the "no add-on" constraint. Typst and Takumi install, but they cannot turn off anti-aliasing. TRMNL cloud Liquid plugins cap payloads at 5 kB and pushes at 12 per hour, and that cap is the root cause of the "max 6 sensors" limits in existing integrations. No surveyed HACS integration serves the TRMNL device API itself, so this niche is open. cryptomilk/hass-eink-dashboard has already proven the rendering stack. The recommendation is still to **build a new integration rather than fork it**. Borrow its proven ideas (and Apache-2.0 code, with attribution). Its absolute-coordinate layout model, card-stored configuration, unauthenticated endpoint and cloud-push TRMNL path are the four things this project would replace.

## Every rendering engine except resvg and Pillow fails a hard constraint

Home Assistant Container is a hostile place for native graphics libraries, and that one fact eliminates most of the field. HA core now requires Python ≥ 3.14.2 and pins `Pillow==13.0.0` ([pyproject.toml](https://raw.githubusercontent.com/home-assistant/core/dev/pyproject.toml), [package_constraints.txt](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/package_constraints.txt)). The image is Alpine-based, and its package list has **no cairo, pango, librsvg or Chromium** ([home-assistant/docker Dockerfile](https://raw.githubusercontent.com/home-assistant/docker/master/Dockerfile)). Custom-integration requirements are installed at runtime by uv, from PyPI plus HA's musllinux wheel index ([util/package.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/util/package.py)), and the container has no compiler. Any dependency therefore needs a cp314 or abi3 **musllinux_1_2** wheel for x86_64 and aarch64, or it does not install. Each candidate was installed in `ghcr.io/home-assistant/home-assistant:stable` (2026.11.0, Python 3.14.10, x86_64) and measured by its share of grey ink pixels. On a 1-bit panel, any grey ink pixel becomes a speckle or a broken stroke.

| Engine | In the HA container | 1-bit-clean output | Cost | Verdict |
|---|---|---|---|---|
| **resvg-py 0.5.0** (MIT) | installs and runs | **yes**: `optimizeSpeed` text and `crispEdges` shapes give 0 % grey | 1.6 MB abi3 wheel; ~38 ms per 800×480 frame | **primary renderer** |
| **Pillow 13.0.0** | already in core | yes: `fontmode="1"` gives 0 % grey | 0 MB; ~100 ms per frame, but you write layout and charts by hand | **compositing and quantising** |
| CairoSVG 2.9.1 (LGPL) | installs, then fails: no `libcairo.so.2` | — | — | not viable |
| skia-python 144.1 | does not install (manylinux only) | — | 14.8 MB | sidecar only |
| Typst 0.15.2 | installs | **no**: 100 % of ink pixels grey, no switch found | 35.8 MB wheel | wrong for 1-bit |
| pytakumi / takumi-py (Satori-style) | installs | **no**: 83 % grey even with font smoothing off | ~6 MB; takumi-py is GPL-3.0 | young, anti-aliased |
| Playwright / Chromium | does not install | no (anti-aliased, must be quantised) | hundreds of MB RAM per session | add-on or sidecar only |
| TRMNL cloud Liquid | n/a (renders in TRMNL's cloud) | browser-rendered | 5 kB payload, 12 pushes per hour, internet required | wrong data path |

Sources for the table: [PyPI resvg-py](https://pypi.org/project/resvg-py/), [PyPI pillow](https://pypi.org/project/pillow/), [PyPI cairosvg](https://pypi.org/project/cairosvg/), [PyPI skia-python](https://pypi.org/project/skia-python/), [PyPI typst](https://pypi.org/project/typst/), [PyPI pytakumi](https://pypi.org/project/pytakumi/), [PyPI takumi-py](https://pypi.org/project/takumi-py/), [PyPI playwright](https://pypi.org/project/playwright/), [TRMNL webhook docs](https://docs.trmnl.com/go/private-plugins/create-a-screen). The install and grey-share figures are the researchers' own tests in the HA container.

The measurements show that **anti-aliasing, not resolution, decides 1-bit quality**. With 14 px Inter, resvg's default `geometricPrecision` gave 82 % grey ink. With `text-rendering="optimizeSpeed"` the same text gave 0 %, at 2.9 ms. Pillow showed the same split: `fontmode="L"` gave 93 % grey, and `fontmode="1"` gave 0 % ([Pillow ImageDraw docs](https://pillow.readthedocs.io/en/stable/reference/ImageDraw.html)). Removing anti-aliasing has a typographic cost. Non-anti-aliased Inter at 14 px has uneven stems, and "H", "N" and "Mon" look semi-bold. The **TRMNL pixel font** (TRMNL12/16/21, SIL OFL 1.1) at its native sizes came out at 0 % grey and looked even in both engines ([bundled OFL.txt](https://raw.githubusercontent.com/cryptomilk/hass-eink-dashboard/main/custom_components/eink_dashboard/fonts/TRMNL/OFL.txt)). This is the non-browser equivalent of TRMNL's own "Pixel Perfect" mode, which exists because anti-aliased greys turn into "random bold or broken glyphs" on 1-bit panels ([TRMNL Pixel Perfect](https://trmnl.com/framework/docs/3.4/pixel_perfect)). The typographic rule is therefore: **TRMNL pixel fonts at 12/16/21 px (or exact multiples) for all small text, and an outline face (Inter, IBM Plex, all OFL 1.1) only for large display numerals**. Large glyphs survive thresholding cleanly ([rsms/inter LICENSE](https://raw.githubusercontent.com/rsms/inter/master/LICENSE.txt), [IBM/plex LICENSE](https://raw.githubusercontent.com/IBM/plex/master/LICENSE.txt)).

SVG wins over hand-written Pillow for a reason that matters for the owner's mockups. Charts, icons, inverted cells, hatched areas and curves are just paths, and the output is deterministic when the renderer is pointed only at bundled fonts. cryptomilk's integration calls `resvg_py.svg_to_bytes(..., font_dirs=[bundled dirs], skip_system_fonts=True)` so that "rendering is identical across HA OS, Docker, and dev machines" ([svg_render.py](https://raw.githubusercontent.com/cryptomilk/hass-eink-dashboard/main/custom_components/eink_dashboard/svg_render.py)). The container has no `/usr/share/fonts` at all, so bundled fonts are mandatory anyway. The one mature project in this space started on Pillow drawing and **replaced it with SVG templates and resvg in v0.2.0**, keeping Pillow only for compositing ([CHANGELOG](https://raw.githubusercontent.com/cryptomilk/hass-eink-dashboard/main/CHANGELOG.md)). SVG's real weakness is that it has no text flow. The integration must measure strings itself to truncate, wrap and right-align figures. My inference: Pillow's `ImageFont` metrics on the same bundled TTFs can serve as the measuring stick. Verify that early, because a metrics mismatch between Pillow and resvg would misalign tabular columns.

The final stage should run in Pillow, with no dithering. UI elements are drawn crisp, so there is nothing to diffuse. Pillow's `convert("1", dither=None)` thresholds at 127, and `quantize()` against a 4-entry palette with `dither=NONE` gives clean 2-bit output ([Pillow Image docs](https://pillow.readthedocs.io/en/stable/reference/Image.html)). The tests also found a trap. On Pillow 13, `Dither.ORDERED` and `Dither.RASTERIZE` produce **byte-identical output to Floyd–Steinberg**, so they are not implemented. If photos or camera stills are ever added, dither them as separate tiles with `epaper-dithering` (MIT, Rust core, musl wheels, 10 algorithms) ([PyPI epaper-dithering](https://pypi.org/project/epaper-dithering/)). Keep it an optional extra, not a core requirement.

## The TRMNL firmware protocol fits in three HA views

Serving the device directly from HA is what makes the system fully local. It also removes every cloud limit. Cloud polling and Redirect need HA reachable from the internet; Redirect has a strict 2-second timeout. Alias keeps image bytes on the LAN but still depends on the TRMNL cloud for check-ins ([Alias plugin](https://help.trmnl.com/en/articles/10701448-alias-plugin), [Redirect plugin](https://help.trmnl.com/en/articles/11035846-redirect-plugin)). Forum users report updates arriving 20–45 minutes late on cloud paths ([HA forum](https://community.home-assistant.io/t/trmnl-e-ink-display/898822)). The firmware protocol is small. It appends the literal paths `/api/setup`, `/api/display` and `/api/log` to the configured base URL, then does a plain GET of `image_url` ([setup.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/src/api-client/setup.cpp), [display.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/src/api-client/display.cpp)). Firmware ≥ 1.4.6 can select a custom server in its captive portal ([LaraPaper README](https://github.com/usetrmnl/larapaper)). The base URL is therefore the HA root, e.g. `http://ha.lan:8123`.

Several protocol details drive the design. The **JSON `status` field controls the flow, not the HTTP status**: 0 means draw, 202 means "not registered, fast-poll", and 500 means reset ([display_session.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/src/display_session.cpp)). The hosted service answers an unknown token with status 500 and `reset_firmware: true`, which makes a real device reset ([TRMNL Display API](https://docs.trmnl.com/go/private-api/screens)). A home server must never copy that behaviour for an auth failure. **`filename` is the cache key**: if it matches the image on screen, the device skips the download and does not refresh the panel at all. Using a content hash of the PNG as `filename` therefore gives "redraw only on change" for free, which saves battery and avoids needless flashes ([display_session.cpp L509-518](https://github.com/usetrmnl/firmware/blob/5246feb/src/display_session.cpp)). Keep it in the documented `<name>-<id>-<unix time>` style, 31 characters or fewer ([BYOS docs](https://docs.trmnl.com/go/diy/byos)). The image limits are strict. The OG has no PSRAM and accepts at most **90,000 bytes**. A BMP must be exactly 800×480, 1 bpp and 48,000 pixel bytes. PSRAM boards such as the TRMNL X accept 750,000 bytes ([config.h](https://github.com/usetrmnl/firmware/blob/5246feb/include/config.h), [bmp.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/lib/trmnl/src/bmp.cpp)). Crisp 1-bit line art compresses well below 90 kB, but the server must still check the size before it hands out a URL. The firmware forces `Accept-Encoding: identity`, follows only one 307/308 redirect and treats 302 as failure. The image view must therefore never gzip or redirect ([http_retry_request.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/src/services/http_retry_request.cpp)).

Authentication needs care, because the firmware cannot send an HA bearer token. Each display poll carries `ID` (the MAC) and `Access-Token`. `/api/setup` carries **no token at all**. The image GET carries `ID` and `Access-Token` only when `image_url` has the same origin as the API base ([request_headers.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/lib/trmnl/src/api-client/request_headers.cpp)). The pattern to copy is HA core's own `ImageView`. It sets `requires_auth = False` and checks credentials inside the handler. It returns **401 only when an `Authorization` header was present and 403 otherwise**, so a misconfigured client does not get its IP banned by the ban middleware ([components/image/__init__.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/image/__init__.py)). Three design choices follow. First, `/api/setup` is open to anyone on the network, so it must hand out an `api_key` only during an explicit **pairing window**: a button entity that opens it for a few minutes, or a MAC the user has pre-registered in the device subentry. Second, generate keys with `secrets.token_urlsafe(32)` and compare them with `hmac.compare_digest`. Third, serve the image from the same origin, so the device authenticates the image fetch with its own token. Non-TRMNL clients get a per-device secret in the URL path. The firmware calls `setInsecure()` on HTTPS, so it does no certificate validation ([http_client.h](https://github.com/usetrmnl/firmware/blob/5246feb/lib/trmnl/include/http_client.h)). The token is therefore low-value by construction. Scope it to "fetch this screen" and prefer the LAN URL over the Nabu Casa URL.

Each poll also carries free telemetry: `Battery-Voltage`, `RSSI`, `Reset-Reason`, `Wake-Time`, `FW-Version`, `Width`, `Height` and `Model` ([request_headers.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/lib/trmnl/src/api-client/request_headers.cpp)). Turning these into HA sensors, plus a "last check-in" timestamp and a "missed check-in" binary sensor, gives battery and liveness alerting through the existing alert path. That serves objectives O2 and O4 directly, which is a stronger justification for this project than the dashboard itself. The `refresh_rate` field also gives server-side sleep scheduling. Return the number of seconds until 06:00 at night, and the panel wakes just after a scheduled layout switch, with no firmware feature involved. Above a 30-minute refresh, the firmware uses a fast refresh instead of a partial one, and it does a full refresh on every 8th update ([display.cpp](https://github.com/usetrmnl/firmware/blob/5246feb/src/display.cpp)).

## One integration, three serving surfaces, rendering kept off the event loop

The integration should be one HACS repo with a **hub config entry and one config subentry per physical screen**. Config subentries are in core since 2025.3 ([dev blog](https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/blog/2025-02-16-config-subentries.md)). This fits the 2026 rule that a device belongs to one config entry and at most one subentry ([dev blog 2026-07-21](https://developers.home-assistant.io/blog/2026/07/21/device-registry-single-config-entry)). Each subentry owns one HA device, its token, its panel profile and its telemetry sensors. It also owns one **`ImageEntity`** that returns cached bytes from `async_image` and bumps `image_last_updated` after each render. That gives a native preview, history and automation triggers. The docs warn that `async_image` runs on every fetch and must stay cheap ([image entity docs](https://contributors.home-assistant.io/core/entities/image/)). The `ImageEntity` itself cannot serve dumb devices, because its `?token=` rotates every five minutes. Devices therefore get the integration's own views instead. That makes three surfaces backed by one cached image: the TRMNL API views, a token-in-path PNG/BMP URL with `ETag`, `Content-Length` and `HEAD` for Alias, ESPHome `online_image`, Kindles and BYOS servers, and the `ImageEntity` for HA itself. ESPHome honours `ETag`, and LaraPaper, Terminus and Alias all accept a plain image URL, so those clients cost almost nothing to support ([ESPHome online_image](https://esphome.io/components/online_image/), [LaraPaper README](https://github.com/usetrmnl/larapaper)).

The render pipeline must follow HA's threading rules strictly. HA flags `open`, `pathlib` reads and `os.listdir` in the event loop ([blocking operations](https://contributors.home-assistant.io/core/internals/blocking-operations/)). Both `ImageFont.truetype` and resvg font loading open files. Load fonts and icons once in the executor at setup. On each render, collect a plain snapshot dict from `hass.states` and the cached service responses in the loop, then pass only that snapshot to `hass.async_add_executor_job`. The pipeline there is: build SVG, run resvg, quantise in Pillow, encode the PNG, check the size. Never touch `hass` from the worker. Trigger renders from `async_track_state_change_event` on exactly the entity IDs the layout references, coalesced with core's `Debouncer` ([helpers/debounce.py](https://github.com/home-assistant/core/blob/dev/homeassistant/helpers/debounce.py)). Add a timer for the clock and the forecasts. Before drawing, hash the snapshot and skip the render when nothing visible changed. A further refinement comes from the official add-on, which renders a fixed lead time (120 s) before the device's next check-in ([trmnl-ha CHANGELOG](https://github.com/usetrmnl/trmnl-home-assistant/blob/main/trmnl-ha/CHANGELOG.md)). The integration knows the `refresh_rate` it handed out, so it can do the same: the panel always gets a fresh image without HA rendering on every sensor tick. The request path itself never renders. **On a failed render it keeps serving the last good image and marks it stale**, as sibbl's tool does with `X-Render-Status: failed` ([sibbl README](https://github.com/sibbl/hass-lovelace-kindle-screensaver)). A diagnostic sensor records the last error and when it happened.

Data sources should use HA's service APIs rather than scraping attributes. Call `weather.get_forecasts` with `return_response=True` for hourly and daily data, cache the result, and refresh it on a weather state change or every 30–60 minutes ([weather/services.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/weather/services.py)). Use `nordpool.get_prices_for_date` from the platinum-tier core Nord Pool integration for today and tomorrow ([nordpool/services.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/nordpool/services.py)). For solar, use the energy platform contract: forecast_solar's `async_get_solar_forecast` returns `{"wh_hours": {iso: wh}}` ([forecast_solar/energy.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/forecast_solar/energy.py)). Fall back to user-chosen sensor attributes, because importing energy internals is fragile. Dependencies should stay at **resvg-py only** in `manifest.json`. Do not pin Pillow, since an exact pin that differs from core's breaks the install. Avoid `Image.getdata()`, which HA's own test config flags as removed in Pillow 14 ([pyproject.toml](https://github.com/home-assistant/core/blob/dev/pyproject.toml)).

## A grid layout with roles makes every sensor optional by construction

The CO2 failure the owner hit is TilmanGriesel/ha_trmnl_weather_station. It logs "No CO2 sensor configured, cannot set up integration", and the maintainer suggested a dummy sensor as the workaround ([issue #16](https://github.com/TilmanGriesel/ha_trmnl_weather_station/issues/16)). The fix request has stayed open since January 2026 ([issue #23](https://github.com/TilmanGriesel/ha_trmnl_weather_station/issues/23)). The failure is architectural: a fixed cloud recipe with a fixed data contract, squeezed into a payload limit ([issue #10](https://github.com/TilmanGriesel/ha_trmnl_weather_station/issues/10)). The new design inverts it. **Setup never validates sensors. Rendering never raises. Every widget declares what it does when its data is absent.** Each widget's data collection runs in its own try/except, so one broken section cannot blank the screen. A missing, `unknown` or `unavailable` value renders as "—" or collapses the widget, and the grid reflows. When a configured entity ID does not exist in the registry, the integration raises a Repairs issue and deletes it once the entity returns. That tells the owner about the problem without breaking the screen. cryptomilk already shows the per-widget half of this: missing entities give "an empty, correctly sized SVG" and non-numeric values format as `--` ([widgets/_helpers.py](https://github.com/cryptomilk/hass-eink-dashboard/blob/main/custom_components/eink_dashboard/widgets/_helpers.py)).

Layout should be a **declarative YAML file per screen**, with a grid as its base, not absolute coordinates. My recommendation is to keep the files under `/config/<domain>/` and read them in the executor. There they are version-controllable, diffable and testable, unlike Lovelace-card storage. The file holds grid columns and rows, a gutter, named slots, and a list of widgets, each with a type, an area span and options. Borrow three things from the TRMNL framework ([framework docs](https://trmnl.com/framework/docs), [Mashup](https://trmnl.com/framework/docs/3.4/mashup), [Value](https://trmnl.com/framework/docs/value)). First, a **named type scale** instead of free pixel sizes, multiplied by the model's `scale_factor` (1.0 on the OG, 1.8 on the X per [trmnl.com/api/models](https://trmnl.com/api/models)), so one layout serves several panels. Second, a first-class footer slot. Third, **bit-depth-aware styles**: hatching on 1-bit, grey fills only when the depth is 2 bits or more. Entities bind through **roles** chosen in the config flow with entity selectors (`weather`, `price`, `solar_forecast`, `rooms[]`, `calendars[]`), and the layout refers to roles, not to entity IDs. That makes a layout shareable between homes, which is what makes it HACS-worthy. Allow HA Jinja only in text slots (headings and labels), rendered per slot under a try/except, as cryptomilk does for headings ([README](https://github.com/cryptomilk/hass-eink-dashboard)). Charts and structure stay as typed Python widgets. A time-of-day **layout schedule** (morning, day and night layouts, each with its own `refresh_rate`) sits on top. No surveyed project offers one, but `/api/display` choosing a layout per poll makes it trivial.

The owner's eight mockups map onto a fixed widget library as follows. Each degradation rule is part of the widget's contract.

| Widget | Data | Hard design point | When data is missing |
|---|---|---|---|
| Now block | weather state, outdoor sensor | large Inter numerals, thresholded | show the parts that exist; "—" for the rest |
| 24 h timeline | Nord Pool prices + solar `wh_hours` (+ hourly temp) | **one shared x-scale object**; price as a step line, solar as a hatched area, a now marker | drop a series; with no series, drop the widget and reflow |
| Hourly table | `get_forecasts` hourly | pixel-font tabular columns that share the timeline's hour ticks | hide rows that have no data |
| Daily forecast | `get_forecasts` daily | **inverted (white-on-black) cell** when gust or rain crosses a user threshold | no inversion when a field is absent |
| Energy flow | power sensors per node | figures set beside the nodes, not on the lines | omit absent nodes and their edges |
| Room temperatures | `rooms[]` role | right-aligned figures, measured with pixel-font metrics | "—" per room |
| Calendar agenda | `calendars[]` role | truncation by measured width | "No events" or collapse |
| Sun / moon | sun entity + computed moon phase | icon paths | computed locally, so it never goes missing |
| Status footer | render time, staleness, device battery | **render timestamp always visible** | always renders |

The shared x-axis is the one place where a widget library beats free-form templates. Price, solar and hourly temperature only line up if they share one scale object, which is also what the layout research recommends. The inverted warning day follows cryptomilk's `invert_condition` precedent on tiles. The always-visible render time answers the most common complaint on the TilmanGriesel tracker, the request to show when the sensor data was taken so stale data is visible ([issue #17](https://github.com/TilmanGriesel/ha_trmnl_weather_station/issues/17)).

## Build new, borrow liberally, do not fork cryptomilk

cryptomilk/hass-eink-dashboard deserves a serious look. It is Apache-2.0, has 131 stars, released v0.9.0 on 2026-10-29, and is pushed weekly. It already proves the in-process SVG, resvg and Pillow stack, bundles the TRMNL fonts, and handles missing entities gracefully ([repo](https://github.com/cryptomilk/hass-eink-dashboard)). Even so, the three options rank as follows.

**Forking is the worst option.** The project moved from v0.2 to v0.9 in about six months, with 22 open issues and PRs. A fork would inherit exactly the parts this project replaces: absolute `x`/`y` widget placement, per-entry widget storage edited through a WYSIWYG Lovelace card, and an image endpoint with `requires_auth = False` and no token at all ([http.py](https://github.com/cryptomilk/hass-eink-dashboard/blob/main/custom_components/eink_dashboard/http.py)). It would then diverge from a fast-moving upstream within weeks. **Contributing everything upstream is the second-best option.** The TRMNL device API is a clean, separable feature that its users would benefit from. The other changes are not: a grid layout model with roles, file-based YAML configuration, and a 1-bit-first style system. Together they amount to a rewrite of the project's core and of its editor UX, which its maintainer has not asked for. Its open issues show it still treats grey as the default: grey text unreadable (#148), a battery outline invisible on a 4-grey panel (#153), and "black text" and "black dividers" added afterwards as options ([issues](https://github.com/cryptomilk/hass-eink-dashboard/issues?q=is%3Aissue)). Upstream adoption is unlikely, and waiting for it would block the owner's mockups indefinitely. **Building new is the right call**, under three conditions. Credit and reuse Apache-2.0 code where it helps, such as font handling and the `optimizeSpeed` / `geometricPrecision` split. License the new project Apache-2.0 so that reuse stays clean. Open an issue upstream offering the device-API view code once it is stable. One trigger reverses the decision: if cryptomilk ships both a device-API server and a grid or slot layout before Phase 2 ends, switch to contributing widgets there.

Publishing to HACS imposes a few constraints that should be set from day one. Use one integration per repo, under `custom_components/<domain>/`, with a manifest that has `domain`, `documentation`, `issue_tracker`, `codeowners`, `name` and `version` ([HACS publish](https://www.hacs.xyz/docs/publish/integration/)). Use a root `hacs.json` with `"homeassistant": "2026.3.0"`, because local `brand/icon.png` images only work from 2026.3 ([brands proxy blog](https://developers.home-assistant.io/blog/2026/02/24/brands-proxy-api)). Add `persistent_directory` if users drop their own fonts into the integration folder ([HACS start](https://www.hacs.xyz/docs/publish/start/)). **The domain must not be `trmnl`**, because core already ships a `trmnl` integration ([core manifest](https://github.com/home-assistant/core/blob/dev/homeassistant/components/trmnl/manifest.json)), and HACS default rejects domains that collide with core ([HACS include](https://www.hacs.xyz/docs/publish/include/)). Testing has changed in 2026. `pytest-homeassistant-custom-component` now declares itself broken, and core publishes **`pytest-homeassistant`** instead ([core package README](https://github.com/home-assistant/core/tree/dev/packages/pytest-homeassistant), [old README](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component)). Pair it with syrupy for state snapshots. Add golden-image PNG tests rendered from fixture states under frozen time with the pinned fonts, and require an exact match. Add one **"empty house" test** that renders every widget and the full layout with zero entities present, which turns the CO2 lesson into a permanent regression gate. hassfest and the HACS action must both pass before HACS default inclusion.

The material risks are known and bounded. First, HA could later add a core route at `/api/log` or `/api/display`, which share HA's `/api` namespace. That is unverified against current routes. The escape hatch is a reverse-proxy path, but the firmware only supports a base URL. Second, core's move from voluptuous to `probatio` in service schemas ([weather/services.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/weather/services.py)) could break custom schema code. Third, combining an update listener with reload methods becomes an error in 2026.12, so use `OptionsFlowWithReload` and nothing else ([dev blog](https://developers.home-assistant.io/blog/2026/05/07/config-entry-listener-together-with-reloading-methods)). Fourth, resvg-py on aarch64 is proven only by its wheel tags, not by a run. That does not matter on ha-host (x86_64), but it does matter for HACS users on Pi hardware. Fifth, some planned details are untested: whether Pillow and resvg metrics agree, and whether the firmware treats 2-bit PNG the same on every OG firmware revision. Phase 0 exists to retire these risks cheaply.

## Conclusion

The research reframes the project. It is less "a prettier dashboard" than **"a local TRMNL server that happens to render"**. The device API, once it runs inside HA, removes the cloud payload limit that crippled the existing integrations. It also turns every panel into a monitored HA device with battery, signal and liveness sensors, which is O2 and O4 work the owner's objectives already demand. The rendering question is mostly settled by HA's Alpine container rather than by taste: only resvg and Pillow survive the "HACS, no add-on, 1-bit-clean" filter. The typographic answer, pixel fonts at native sizes for small text, matters more to perceived quality than the choice of engine.

The non-obvious design lever is the **filename-as-content-hash and `refresh_rate` pair**. Together they let the server decide when the panel flashes and when it sleeps, so battery life, ghosting and night scheduling become server logic instead of firmware features. The most durable engineering asset is the "empty house" golden test, not any widget. It guarantees that the next home with no CO2 sensor, no solar panels and no Nord Pool entry still gets a correct, quiet screen.
