# Internationalisation (0.2.0)

**Decision (owner, 2026-11-09):** "we ship with english default and optional swedish", other
languages when contributors add them. It ships in 0.2.0. **The default is British English**
(owner: "it should be Brittish English as default"): `en` uses British spelling (colour,
metre, centre, grey) and conventions (day before month: "Sunday 8 November", 24-hour clock),
in the drawn texts and in Home Assistant's UI texts.

## How other HACS projects do it

- **Text in Home Assistant's own UI** (config flow, options, Repairs, entity names): HA's
  translation system. `strings.json` is the English source; `translations/<lang>.json` holds
  each language; HA picks the user's language and falls back to English. Contributors add a
  language with one new file in a pull request. Paperboard already does this (en, sv).
- **Text the project draws itself** (Lovelace cards, image renderers): HA's system does not
  reach it. Cards such as Mushroom ship `translations/<lang>.json` plus a small `localize()`
  helper with an English fallback per key. Contributors add a language the same way.

Paperboard draws its text into an image, so it needs the second pattern next to the first.

## Design

1. **Files.** `custom_components/paperboard/i18n/en.json` is the source of truth, every key
   present. `sv.json` has the same keys. Flat-ish JSON grouped by area:
   `date.weekday[7]`, `date.weekday_short[7]`, `date.month[12]`, `date.today`, `date.tomorrow`,
   `date.week_short`, `date.week`, `weather.condition.<ha_state>`, `weather.prose.*`,
   `label.*`, `energy.*`, `flow.*`, `chart.*`, `agenda.*`, `holiday.<english name>`,
   `layout.<id>` (display names), `section.*` (widget titles in bundled layouts).
   Placeholders use `{name}` (`str.format`).
2. **Loading.** `i18n.py`: `load_catalogs()` reads every `i18n/*.json` once, in the executor
   at setup (never on the event loop), into an immutable dict. Tests call it directly.
3. **Language resolution.** `resolve(hass_language, available)`: exact (`pt-BR`), then base
   (`pt`), then `en`. A layout's `lang:` pin accepts `auto` or any available language.
   `Snapshot.lang` default becomes `en`.
4. **Lookup.** `t(lang, key, **kw)` returns the language's text, else English, else the key
   itself (visible, never an exception: rendering never raises). Lists (weekday, month) via
   `tl(lang, key)`.
5. **Holidays.** HA's holiday calendar names events in English; `holiday.<English name>`
   translates them when the language has an entry, otherwise the name is kept.
6. **Prose (headline).** Per-language templates (`weather.prose.join` = `"{a} and {b}"` /
   `"{a} och {b}"`, range and temperature phrases), no grammar in Python.
7. **Layout texts.** Bundled layouts use keys: `title: {key: section.home}`. User layouts keep
   plain strings or `{en: …, sv: …}` dicts (0.1.2 behaviour). `layout_text()` handles all
   three. Layout ids stay (`tidslinjen` …) so existing configs keep working; the dropdown
   shows `layout.<id>` (en "Timeline", sv "Tidslinjen").
8. **Numbers.** `fmt.*` default `lang="en"` (decimal point); every caller passes
   `snap.lang`. The comma set stays.
9. **HA UI texts.** `strings.json` audit: English first and complete; `translations/sv.json`
   complete. No change of mechanism.
10. **Contributing.** CONTRIBUTING "Add a language": copy `i18n/en.json` and
    `translations/en.json` to `<lang>.json`, translate, run the parity test, open a PR.

## Release

0.2.0: a minor version, because layout display names change for English users (Timeline
instead of Tidslinjen) and the layout `lang:` pin accepts any available language. Configs keep
working: layout ids do not change. The 0.1.2 tag stays local unless the owner pushes it.
